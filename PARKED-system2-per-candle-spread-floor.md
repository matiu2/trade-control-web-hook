# PARKED — System 2 per-candle spread stop floor

**Status:** PARKED INDEFINITELY, 2026-09-16. Superseded by the baked spread
mask. Branch `sl-spread-floor-per-candle` is **not** to be merged; this document
replaces it.

**Operator's call:** *"sl-spread-floor-per-candle can be parked forever. We now
have that system that samples spread size in all instruments and bakes them into
the program."*

---

## What it was going to do

Replace System 2's one-shot widen/restore latch with a rule evaluated on EVERY
candle, not just inside a baked spread hour:

```
sl_distance = max(original_distance, SL_MIN_SPREAD_MULTIPLE × live_spread)
```

So the stop tracks the spread continuously, and also catches unpredictable
off-hour flares.

## Why it was proposed (operator, 2026-07-29)

CFD prices are broker-made. During a low-liquidity window (07:00–08:00 Brisbane
for GBP/NZD: NZ banks only, or just the broker in-house) a b-book broker can run
a synthetic wick and stop us out. A stop held at 10× the *live* spread absorbs
that whiplash; once Sydney liquidity returns, price is expected back near where
it was. Deliberately UNCAPPED — the wide stop is absorbing a synthetic spike,
not a real move.

## The bug it was going to fix

`restore_bar` (replay) / `blackout_watch` (live) restore on a FLAT
`SPREAD_BLACKOUT_RECOVERED_PIPS = 4.0`. GBP/NZD's calmest hour is 8.6p, so for
that instrument the recovery branch is **unreachable** and restore falls through
to the 12h backstop — observed as a widen 06:30 → restore 18:00 that should have
been ~08:00.

A per-candle `max()` dissolves that: no threshold to be unreachable, and no
backstop on the normal path.

## Why it is parked instead of built

The **baked spread mask** (`core/src/spread_baseline_candle.rs`, generated by
`spread-baseline-gen`) now carries real measured per-instrument spread shape —
160 rows, per-hour statistics, from actual sampled data. That addresses the same
root cause from the other end: rather than re-deriving the right stop from a
live quote every candle, the system already knows what each instrument's spread
does in each hour, per instrument, and gates on that.

See the memories `spread_hour_mask_baked_not_cron_generated` and
`spread_hour_shape_varies_by_instrument` — the latter is the measurement that
makes the flat 4.0p threshold's failure legible (EUR/USD recovers mid-hour on
64% of days, GBP/AUD on 0%, and Gold's mask is empty entirely). A single flat
constant was never going to serve all three; the baked mask is how that is
handled now.

## What was NOT broken (verified 2026-07-29, still true)

Worth keeping, because these were checked and cleared at the time and a future
reader may otherwise re-investigate them:

- **System 3 (resting orders)** — `off_now` checks `!is_spread_hour` FIRST, so it
  restores at the baked hour end (08:00) and never reaches the 4.0p threshold.
  Its re-drive goes through `run_enter`, which re-reads a FRESH spread, re-applies
  `widen_sl_to_spread_floor`, and re-sizes off the widened SL. The sub-1R cancel
  is the existing `SlWiden::Reject` branch. All three behaviours the operator
  asked about already ship.
- **The widen SIZE was never broken** — the observed 49.8p matched the baked p90
  (50.0p) exactly. Only the RESTORE latched.

## The open question it never answered

The branch's TODO had six steps, all unchecked. Five were implementation. The
sixth was a genuine design question that anyone reviving this idea must answer
first:

> **Break-even precedence** — if break-even has armed and moved the stop to the
> fill, and the spread floor then wants the stop WIDER, which wins?

Widening past a break-even stop re-introduces risk on a trade the operator has
already de-risked. Holding break-even means the floor does not protect the trade
it exists to protect. There is no obviously-correct answer, which is why the
branch stopped here.

Note this is the same precedence question that recurs elsewhere in the codebase
(`blackout_apply`'s `may_widen` guard exists for exactly this reason — live
refuses to widen a break-even stop, and the replay's parity with that was audit
finding #5, fixed 2026-09-13).

## If this is ever revived

1. Answer the break-even precedence question **first**. It is the reason this
   stalled, not the code.
2. Do not start from the branch. It is ~240 commits behind `main` and conflicts
   in 28 regions, most of them in `core/src/intent/sl_spread_floor.rs` — which was
   substantially rewritten on 2026-09-15 when the tick-grid snap moved INSIDE
   `widen_sl_to_spread_floor` (its signature now takes `tick_size`). Re-derive
   against current `main`.
3. Check first whether the baked mask has already made the case moot. The
   motivating GBP/NZD incident was a *restore* that latched; confirm that still
   happens before rebuilding anything.
